给 149 篇存量文章补 Mermaid 图

文章写了两年多，代码块很多，图很少。之前想过配图，走的是文生图那条路：写提示词、找后端、生成 PNG、再传进仓库。这条路走了一半就停了——不是提示词写不出来，是这样出来的图有三个绕不过去的问题。

  • 改不动。 图是一张位图，正文里某个类名改了，图里还是旧名字。
  • 对不上。 深浅色主题切换时，位图的底色和正文背景不是一套色，永远有一块方形的异色区域。
  • 审不了。 PNG 进 Git 是一个二进制块，review 时看不到改了什么。

Mermaid 把这三件事反过来：图是文本，能 diff、能跟着主题变量走、能在窄屏上按容器重新排版。所以这次全站补图，只做 Mermaid，不做位图。

第一道坎：配置开了，图不渲染

Butterfly 主题本身支持 Mermaid，配置也简单，改 _config.butterfly.yml：

mermaid:
  enable: true
  code_write: true
  theme:
    light: default
    dark: dark
  zoom_pan: true

改完写一个代码块，渲染出来的不是图，是源码本身。

问题不在 Mermaid，在 prismjs。渲染链路是这样的：

flowchart TD
    A[Markdown 里的 mermaid 代码块] --> B[hexo-renderer-marked 转成 pre code]
    B --> C{prismjs 是否接管}
    C -->|接管| D[输出 code class=language-mermaid 并插入高亮 span]
    C -->|放行| E[输出 code class=mermaid]
    D --> F[主题脚本找不到 target]
    E --> G[主题脚本渲染成 SVG]

主题脚本找的是 article-container 里的 pre > code.mermaid。一旦 prismjs 先接管，类名变成 language-mermaid，里面还塞满了高亮用的 span，选择器直接落空，页面就只剩一个灰色的代码块。

修法是在根目录的 _config.yml 里让 prismjs 放过 mermaid：

prismjs:
  enable: true
  exclude_languages:
    - mermaid

注意是排除语言，不是排除文件。我试过另外两条路，都不通：

尝试结果
在 prismjs 下加 prismjs_excludehexo 不认这个键，静默忽略
在 include 里加 [".md"]include 只作用于 source/ 目录的搬运，不会让 markdown 绕过渲染

验证办法很直接，生成完数一遍：

grep -rl 'class="mermaid"' public --include='*.html' | wc -l   # 51
grep -rl 'language-mermaid' public --include='*.html' | wc -l # 0

前者是真正渲染的页数，后者必须是 0。只要第二个数字不是 0，说明还有页面被 prismjs 截走了。

哪些文章需要图

149 篇里不是每篇都该加图。给一篇命令清单硬塞一张流程图，图不解释任何东西，只增加滚动距离。我用的判定口径：

文章形态加不加理由
时序图场景（多角色调用、重试、超时）加文字描述顺序最容易读错
流程分支（状态判定、拒绝策略、降级）加分支用文字写就是嵌套 if 的散文
架构与数据流（组件通信、请求链路）加一张图省掉三段解释
类关系（继承、组合、职责链）加文字写关系比写结论慢十倍
单纯概念讲解不加图会是正文的复读
命令与配置清单不加顺序本身就是内容，图是多余的框
单文件配置说明不加没有跨组件关系可画

还有一个特例：正文里已经有 ASCII 画的图，改成 Mermaid。手写的 ASCII 图有三个毛病——等宽字体下宽度算不准，窄屏会折行错乱；改动一个节点要对齐一片空格；深浅色主题下没有颜色语义。这类图全部替换。

批量插入 23 张类图

23 篇设计模式文章结构高度一致，符合批量处理的条件。插入点是固定的：## 什么是 X 模式？ 或 ## 实现模式 标题后的第一段之后。

一开始我按”插入到常见标题之后”来做，结果有一半的图跑到了 ## 问题背景 之前，甚至跑到文末。原因是这些文章的标题写法并不统一，脚本命中的位置各不相同。这是批量改造里最容易踩的一类坑：你以为结构一致，其实只是看起来一致。

改成先探测每篇实际存在的标题，再按优先级选第一个命中的锚点，同时立刻检查插入点前后各 5 行确认落位，才对上。

类图本身不复杂，以观察者模式为例：

classDiagram
    class Subject {
        <<interface>>
        +attach(o)
        +detach(o)
        +notify()
    }
    class ConcreteSubject {
        -observers
        +getState()
        +setState()
    }
    class Observer {
        <<interface>>
        +update()
    }
    class ConcreteObserver {
        -state
        +update()
    }

    Observer <|.. ConcreteObserver
    ConcreteSubject --> Observer : notify

窄屏上横版图被压成 17px（以及它背后更普遍的问题）

这是这次改造里唯一一个真 bug，也是唯一一处必须改主题文件的地方。

桌面端 51 页 52 张图全部正常。切到 390px 宽度再跑一遍，发现 4 个页面的横版图高度只有 17–19px——图还在，只是被压成了一条线。

第一层根因是两处规则的叠加：

flowchart TD
    A[mermaid 输出 width=100% 与原始排版宽度的 viewBox] --> B[主题 CSS 规定 max-width 100% height 100%]
    B --> C[高度不再由宽高比决定 而被容器高度约束]
    C --> D[扁平宽高比在大高度约束下被压成一条线]
    D --> E[390px 视口下 SVG 高度只剩 17px]

把 height: 100% 改成 height: auto，高度回到宽高比手里，17px 的问题消失了。但只改这一条，等于把一个更普遍的问题留在了原地：只要 SVG 永远铺满容器宽度，它的显示比例就永远是「容器宽 ÷ viewBox 宽」——窄图被放大、宽图被压小，两个方向都失真。

实测（1440px 下正文列宽 690px）：

图的 viewBox 宽显示宽度缩放正文字号
1836903.77×约 60px
2766902.50×约 40px
5686901.22×约 20px
9086900.76×约 12px
15756900.44×约 7px

390px 视口下更极端：1575px 宽的图缩到 0.22 倍，字号只剩 3px——图还在，但已经读不了了。

这里有两个容易走错的判断。

一、不要去找「原始渲染宽度」。 运行时实测：mermaid 输出的 SVG 属性是 width="100%"，没有 data-width，也没有内联 max-width，viewBox 就是它排版时用的宽度。也就是说并不存在一个「被压小之前」的宽度可以还原，只能自己定规则。

二、不要只在「缩小」方向设阈值。 只拦「压得太狠」的话，183px 的图仍然会被放大 3.77 倍，字号 60px 比正文还大，同样难读。

正确的规则是给显示宽度一个区间：

显示宽度 D = clamp(容器宽, 0.75 × 排版宽, 排版宽)

即绝不放大（缩放系数 ≤ 1）；最多缩到 0.75 倍（字号 16 × 0.75 = 12px，刚好是可读下限）；再窄就不再缩，交给容器横向滚动。

修法分两处：

// 容器：允许横向滚动
.mermaid-wrap
  width: 100%
  overflow-x: auto

// SVG：高度交给宽高比，不要再锁 100%
.mermaid-wrap > svg
  height: auto

主题脚本里按上面的规则定尺。注意 max-width 必须和内联 width 一起写：主题 CSS 的 max-width: 100% 会夹住内联 width，只写 width 的话宽图会被夹回容器宽，横向滚动就失效了。

const minReadableScale = 0.75

const fitMermaidSvg = svg => {
  const wrap = svg.parentElement
  if (!wrap) return
  const box = wrap.getBoundingClientRect()
  const vb = parseViewBox(svg.getAttribute('viewBox'))
  if (!box.width || !vb || !vb[2] || !vb[3]) return
  const natural = vb[2]                    // 排版宽度，同时是显示宽度的上限
  const target = Math.min(natural, Math.max(box.width, natural * minReadableScale))
  svg.style.maxWidth = natural.toFixed(2) + 'px'   // 必须一起设，否则会被主题 CSS 夹回去
  svg.style.width = target.toFixed(2) + 'px'
  svg.style.height = 'auto'
}

出图后立即调用一次，视口变化时整体重排一次：

window.addEventListener('resize', () => {
  requestAnimationFrame(() => {
    document.querySelectorAll('.mermaid-wrap > svg').forEach(fitMermaidSvg)
  })
})

改完全站复测（54 个页面 / 122 张图，1440 与 390 两档）：

缩放系数区间0.22 – 3.770.75 – 1.00
最小正文字号约 3px约 12px
渲染失败（.mermaid-error）00
页面级横向溢出00

宽图在窄屏变成可以横向拖动的长图，竖版图没有任何回归。

顺带一提，改完主题文件后本地预览必须重启 hexo server。.pug 里的内联脚本是渲染期编译的，热重载不会重新载入，看到的一直是旧行为——这一条浪费了我两轮排查。

三个会让解析失败的写法

批量写了 52 张图，语法问题集中在三处，都是”看着没问题、跑起来报 Parse error”的类型。

一、节点标签里不能有英文双引号。

flowchart LR
    A["@DS("slave") 注解"] --> B[路由]

第二个引号会提前闭合字符串。改成中文引号或去掉：

flowchart LR
    A["@DS 注解（slave）"] --> B[路由]

二、边标签里的括号会破坏语法。

flowchart TD
    A[注册] -->|this.sendWelcomeEmail()| B[发信]

报错是 Parse error on line 4 ... Expecting。把标签整体加引号即可：

flowchart TD
    A[注册] -->|"this.sendWelcomeEmail()"| B[发信]

三、行尾多一个逗号。 节点定义里的尾逗号会让解析器停在那一行，而且报错位置经常指向上一个节点，不好定位。

这三条写成一个 lint 脚本扫全文，比渲染后一张张看快得多：

// 扫所有 mermaid 块：标签内双引号、边标签尾逗号
const bad = []
for (const block of blocks) {
  const lines = block.split('\n')
  lines.forEach((line, i) => {
    const label = line.match(/\[([^\]]*)\]|\|([^|]*)\|/)
    if (!label) return
    const text = label[1] ?? label[2] ?? ''
    if (/"/.test(text) && !/^".*"$/.test(text.trim())) bad.push([i, 'unbalanced quote', line])
    if (/,\s*$/.test(text)) bad.push([i, 'trailing comma', line])
  })
}

校验：双视口全量跑一遍

图这种东西，肉眼看不出来哪一张坏了。我用 Playwright 跑全量断言，两个视口各一遍：

const pages = await readPageList() // 51 个 URL
for (const viewport of [1440, 390]) {
  for (const url of pages) {
    const r = await page.evaluate(() => ({
      wraps: document.querySelectorAll('.mermaid-wrap').length,
      errors: document.querySelectorAll('.mermaid-error').length,
      emptySvg: [...document.querySelectorAll('.mermaid-wrap svg')]
        .filter(s => s.getBoundingClientRect().height < 30).length,
      overflow: document.documentElement.scrollWidth - innerWidth,
    }))
    // 任何一项不达标就记进 bad
  }
}

断言四项：图容器数量与预期一致、没有渲染错误节点、没有高度塌陷的 SVG、没有横向溢出。

最终结果：

pages 51 / totalDiagrams 52 / bad []
1440 viewport: ok
390  viewport: ok

小结

这次改造真正花时间的不是画图，是三个”配置看起来对了但结果不对”的点：

  1. Mermaid 的开关有两个。 主题里的 mermaid.enable 决定要不要渲染，根配置里 prismjs.exclude_languages 决定渲染器能不能拿到它。少任何一个，页面都只剩源码。
  2. 图尺寸失真不是”能不能还原”的问题，是”要不要设上限”的问题。 SVG 铺满容器，等于把显示比例交给了容器宽度：窄图被放大到 60px 字号，宽图被缩到 3px。规则必须写成区间——绝不放大、最多缩到 12px 字号、再窄横向滚动。
  3. 批量改造的锚点要靠探测。 “看起来结构一致”和”结构真的一致”是两回事，脚本必须自己确认落位。

图这件事和注释有点像：它不是给作者看的，是给半年后的自己和恰好路过的读者看的。文字能说清的地方不必画，说不清的地方，一张图能省掉三段解释。
