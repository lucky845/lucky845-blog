【AI】给 AI Agent 设计工具：接口写得好，模型才用得对

发表于2026-11-09|更新于2026-11-09|AI
|浏览量:

1. 一个被低估的事实：模型是照着你的描述调工具的

绝大多数 Agent 跑不对，不是因为模型笨，是因为工具描述写得不像话。

模型看到的东西只有：工具名、描述、参数 schema。它没见过你的代码，不知道 get_user 内部到底查的是主库还是缓存，也不知道 status: 1 到底是「正常」还是「已删除」。

所以工具设计的本质是：把「人读了代码才知道的隐含契约」，翻译成模型能读的显式描述。

这条认知一旦确立，很多设计决策就顺了。

2. 工具粒度：少了不够用，多了选不对

工具太少，模型要绕好几步才能完成一件事；工具太多，就会选择困难——尤其当两个工具语义高度重叠时。

判断粒度是否合适的经验法：

  • 一个工具只做一件语义完整的事。update_order 好过 update_order_status + update_order_address + update_order_note 三个，除非权限模型确实要求分开。
  • 不要暴露「内部步骤」。begin_transaction / commit 这种就不该给模型，它没有事务生命周期的心智模型。
  • 同类操作合并成列表式接口。一次查 10 个 id，好过一次查 1 个——少一轮对话，少一次出错机会。

反面例子：

{
  "name": "do_something",
  "description": "处理数据"
}

模型看到这个只能瞎猜。正确写法：

{
  "name": "query_user_by_email",
  "description": "按邮箱地址精确查询单个用户的账户信息，返回昵称、注册时间、会员状态。邮箱不存在时返回 found=false，不会报错。只支持查一个邮箱，批量查询请调用 batch_query_users。",
  "parameters": {
    "type": "object",
    "properties": {
      "email": {
        "type": "string",
        "description": "完整的邮箱地址，必须包含 @ 和域名，不要传用户名或手机号"
      }
    },
    "required": ["email"]
  }
}

注意这段描述里塞进去的四类信息：

  1. 做什么（按邮箱查用户）
  2. 返回什么（昵称、注册时间、会员状态）
  3. 边界行为（不存在时返回 found=false 而非抛异常）
  4. 不该用它做什么（批量查询请换工具）

第 3、4 条最常被漏掉，也最容易让模型犯错。

3. 参数设计：枚举优于自由文本，结构化优于拼接

参数越多，模型出错的概率越高。几个硬性建议：

  • 能枚举就枚举。status: "active" | "inactive" 远好过 status: string。
  • 能拆成多个字段就别拼字符串。start_time + end_time 好过 time_range: "2026-11-01~2026-11-09"。
  • 时间统一用 ISO 8601 带时区，并写进描述；否则模型会传「明天」「上周五」。
  • 必填项越少越好，可选参数给默认值并写清楚默认值是什么。
  • 不要既传 id 又传 name，模型会自相矛盾，服务端要定清楚谁优先。

数值型参数还有一个坑：模型经常传字符串 "10" 而不是数字 10。如果你的 SDK 做严格校验会直接失败，建议在服务端做一次宽容转换，但要记录日志统计这种情况——如果频繁出现，说明描述里没讲清楚。

4. 错误信息：写给模型看的，不是写给日志看的

这是投入产出比最高的一处改进。

大多数工具返回的错误长这样：

{"error": "Invalid parameter"}

模型拿到这句什么也学不到，只能原样重试或者换个猜法。改成这样：

{
  "error": "parameter_invalid",
  "field": "email",
  "message": "email 参数缺少 @ 符号。当前收到：'zhangsan.example.com'。请传入完整邮箱，例如 zhangsan@example.com。",
  "retryable": true
}

关键字段的作用：

字段作用
error机器可读的错误码，便于统计和分支
field哪个参数错了，模型能精准修正
message人话说明 + 当前收到的值 + 正确的样子
retryable模型据此决定是重试还是换路

retryable 这个字段特别重要。参数错可以重试，权限不足重试一万次也没用——明确告诉模型「别试了」，能省下大量 token 和时间。

sequenceDiagram
    autonumber
    participant LLM as 模型
    participant T as 工具
    participant API as 下游服务

    LLM->>T: 调用（参数 A）
    T->>API: 转发
    API--xT: 400 参数错误
    T-->>LLM: {error: INVALID_PARAM, field: page_size,<br/>message: "应为 1-100，收到 1000", retryable: true}
    Note over LLM: 读到 field 与正确范围<br/>只改这一个参数
    LLM->>T: 调用（参数 A 已修正）
    T->>API: 转发
    API-->>T: 200 OK
    T-->>LLM: 结果

注意失败那次返回的不是 exttt{「请求失败」}四个字，而是哪个字段错、错成了什么、正确范围是什么。这就是「错误信息写给模型看」的具体含义：同样的失败，模型能否一次改对，差别全在这段文本里。

5. 幂等：Agent 一定会重试，你必须扛得住

模型重试的频率远超人的想象：网络抖动、超时、结果不理想，它都会重来一次。如果你的写操作不幂等，就会重复下单、重复发邮件、重复扣款。

最低成本的做法是 idempotency key：

POST /orders
Idempotency-Key: <模型生成的 UUID，同一意图内保持不变>

服务端在 24 小时内对该 key 去重，命中则直接返回首次结果。

如果没有幂等机制，退而求其次：让所有写操作都变成「先查后写」，并在描述里明确告诉模型「调用前请先查询是否已存在」。但这是靠模型自觉，不可靠。

6. 危险操作：默认不暴露，暴露也要二次确认

能删数据的工具、能转账的工具、能发外部请求的工具，这三类要格外小心。

实践中的分层做法：

  • 默认不给。Agent 的主循环里不挂载危险工具，需要时通过独立子任务临时授予。
  • 必须确认。高危操作返回一个 requires_confirmation 标记，让上层 UI 弹确认，模型不能自己确认。
  • 限定范围。delete_file 只允许操作某个白名单目录，越界直接拒绝并说明原因。

这和 Prompt Injection 的防御是同一个思路：不要指望模型判断得对，要在架构上让它做不对的事做不到。

7. 工具返回值：小而准，别塞全量数据

模型上下文是稀缺资源。一个工具返回 200 条记录，直接吃掉几千 token，还把重要信息稀释掉。

  • 返回摘要 + 分页游标，让模型按需取下一页。
  • 字段名用业务语义，别用 field1、f2。
  • 时间、金额带单位："amount": "12.50 CNY" 好过 "amount": 1250。
  • 空结果要明确说：{"items": [], "total": 0, "hint": "没有符合条件的订单"}，别返回 null 让模型猜。

8. 一份可用的自检清单

上线前逐条对一遍：

  • 每个工具的描述里，是否写清楚了「做什么、返回什么、异常时返回什么、不要用它做什么」
  • 参数是否有枚举约束，时间是否统一格式
  • 错误信息是否包含字段名、当前值、正确示例、是否可重试
  • 写操作是否幂等
  • 危险操作是否有确认机制和范围限制
  • 返回体是否足够小，是否支持分页
  • 工具之间是否存在语义重叠，重叠的原因是否合理

这七条不涉及任何模型能力提升，但能把 Agent 的工具调用成功率拉高一大截——因为大部分失败本来就不是模型的问题，是接口没写清楚。
