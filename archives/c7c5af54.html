【博客】不换主题改外观：给 Butterfly 叠一层纯 CSS 皮肤

发表于2026-11-10|更新于2026-11-10|技术笔记
|浏览量:

给 Butterfly 叠一层纯 CSS 皮肤

博客跑了两年，主题是 Butterfly。看久了想换点样子，摆在面前有三条路：

  • A：只换配色。 成本最低，拿主题自带的配色方案切一下。问题是换完还是那个主题，只是换了个色。
  • B：纯 CSS 覆盖。 不动模板、不动正文，用一个独立样式表叠在上面。所有改动集中在自己的文件里，主题升级时冲突面可控。
  • C：换主题。 视觉效果上限最高，但要重新接 Mermaid、评论、搜索、目录，还得把两年的样式微调全部重做。

选了 B。它的约束很明确，也正因为明确而好决策：不能改 DOM，只能改样式。这意味着所有效果必须靠现有选择器做出来，做不到的就是做不到，不会陷入”改着改着把模板改烂了”的泥潭。

皮肤怎么挂上去

Butterfly 的注入点是现成的。_config.butterfly.yml 里有两段自定义注入：

inject:
  head:
    - <link rel="stylesheet" href="/css/schematic.css?v=1">
  bottom:
    - <script src="/js/schematic-marks.js?v=1" defer></script>

样式表放在 source/css/，脚本放在 source/js/，构建时会被原样搬到 public/。顺序上它在主题样式之后加载，所以同等优先级下能覆盖主题规则；但优先级相同时靠顺序赢，优先级不同时顺序没用——这一点决定了后面大部分改法都得用更具体的选择器，而不是简单地再写一遍。

第一个坑：变量覆盖把顶栏 links 变成了看不见的字

皮肤的第一版很克制：改了一批 CSS 变量，其中一个是边框色。

:root {
  --sc-line: #DDE1DE;
  --light-grey: var(--sc-line); /* 这一行是罪魁 */
}

改完发现顶栏的菜单链接全都看不见了——不是被遮住，是颜色几乎和底色一样。

链路是这样的：

flowchart TD
    A[覆盖 --light-grey 为浅色] --> B[主题的 nav 链接颜色取自 --light-grey]
    B --> C[链接变成浅色]
    C --> D[但 nav 在首屏上是浅底玻璃效果]
    D --> E[浅色字压浅色底 对比度接近 0]

变量的名字叫 --light-grey，看起来像”浅色装饰”，实际被当作顶栏链接的前景色在用。这种”变量名描述颜色、变量用途却是语义”的情况是覆盖第三方主题时最常见的一类事故：你以为改的是装饰，其实改的是可读性。

教训不是”别覆盖变量”，而是：覆盖变量之前，先查清这个变量被谁用、用在哪。 查法很简单：

grep -rn "var(--light-grey)" themes/butterfly/source/css | wc -l
grep -rn "var(--light-grey)" themes/butterfly/source/css

数一下有几十处，再看一眼它们分别是什么属性，就知道这个变量能不能碰。

修法是把顶栏从”浅底浅字”改成”深底浅字”，并且在皮肤里把需要用到的颜色全部显式写死，不再依赖主题变量：

#nav {
  background: rgba(9, 14, 18, 0.78);
  backdrop-filter: blur(12px);
  height: 56px;
  border-bottom: 1px solid rgba(255, 255, 255, 0.08);
}
#nav .site-name,
#nav .nav-site-title { color: rgba(240, 243, 241, 0.96); }
#nav .site-page {
  color: rgba(221, 225, 222, 0.78);
  font-family: var(--sc-mono);
  font-size: 13px;
}
#nav .site-page:hover { color: #fff; }

菜单项再加一条下划线动效，用伪元素从中间展开：

#nav .menus_item > a { position: relative; padding: 0 10px; }
#nav .menus_item > a::after {
  content: '';
  position: absolute;
  left: 50%;
  right: 50%;
  bottom: 8px;
  height: 2px;
  background: var(--sc-mark);
  transition: left 0.18s ease, right 0.18s ease;
}
#nav .menus_item > a:hover::after { left: 10px; right: 10px; }

第二个坑：clean-css 把媒体查询整段吞了

移动端要加大触控目标，写了一条：

@media (pointer: coarse) {
  #nav .toggle-menu { min-width: 44px; min-height: 44px; }
}

本地开发没问题，构建完打开一看，这条规则不在生成的 CSS 里。

hexo 的 clean-css 会把”它认为不必要”的媒体查询合并掉，而 pointer: coarse 这种特性查询在它的判定里属于可以丢弃的那一类。试了合并条件：

/* 前一个条件被丢弃，只留下 pointer 这一半 */
@media (max-width: 991px), (pointer: coarse) { ... }

结果更糟：宽度条件被删掉了，规则只在粗指针设备生效，窄窗口的桌面浏览器拿不到。

最后能保住的写法是在逗号后留一个空格：

@media (max-width: 991px), (pointer: coarse) { ... }

两块都留下来了。这类问题很难从源码看出来，因为源码是对的，是压缩器改了语义。可靠的做法是在产物里验证，而不是在源码里推理：

grep -o "@media[^{]*{" public/css/schematic.css | sort -u

把产物里实际存在的媒体查询列出来，跟你写的对一遍。少一条就是被吞了。

第三个坑：改了没生效，因为被缓存了四小时

改完样式部署，刷新页面——没变化。

这个问题的迷惑性在于：本地是对的，产物是对的，线上是旧的，所以第一反应会去怀疑构建或者注入没生效。实际原因是 CDN：

curl -sI "https://blog.lucky845.top/css/schematic.css" | grep -i "cache-control\|age"
# cache-control: max-age=14400
# age: 86

/css/*.css 被缓存 4 小时。改文件名之外的内容，对 CDN 来说什么都没发生。所以皮肤的资源都带版本号：

<link rel="stylesheet" href="/css/schematic.css?v=4">

改样式 → 升版本号 → URL 变了 → CDN 必须回源。

但这里还有个更隐蔽的连带问题。主题自己的 index.css 的缓存指纹是主题版本号，不是内容哈希：

<link rel="stylesheet" href="/css/index.css?v=5.7.1.260810">

这意味着如果你改的是主题变量驱动的样式（比如首屏图片高度 index_top_img_height），index.css 的内容变了，但 URL 没变，线上会继续用旧 CSS。而它和皮肤是两个文件、两条缓存链路。

解法是借皮肤的 URL 变化把整页的缓存一起冲掉——把查询串挂在皮肤上，同时改动主题配置：

<link rel="stylesheet" href="/css/schematic.css?v=5&amp;t=300">

URL 变了，浏览器重新请求整页资源，index.css 也跟着重新拉一次。这不是最优雅的方案（更干净的做法是给所有静态资源加内容哈希），但在四小时缓存和主题版本号固定的前提下，它是最小的可行改动。

不能省的三件事

改造过程中有三条底线，属于”效果再好也不能破”的那一类。

正文最小字号 12px。 皮肤容易越改越小，尤其是为了塞下更多信息的时候。批量验证：

const small = [...document.querySelectorAll('main *')].filter(el => {
  const size = parseFloat(getComputedStyle(el).fontSize)
  return size > 0 && size < 12 && el.textContent.trim()
})

触控目标不小于 40px。 移动端的导航按钮、目录条目、图表工具条都要过一遍。这条和上一条会打架——大触控目标通常意味着大字号或者大留白，最后靠 min-width / min-height 单独撑开交互区域，不动字号。

尊重 prefers-reduced-motion。 皮肤里有一百多处过渡和动画，全部包起来：

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}

顺带一提，这一条也容易在压缩环节出问题，同样要去产物里确认它还在。

小结

纯 CSS 覆盖这条路，收益是可控，成本是所有效果都要迁就现有 DOM。真正花时间的不是写样式，是三件和样式无关的事：

  1. 覆盖变量前先查用途。 变量名描述颜色，用途可能是语义。--light-grey 被当作顶栏前景色用，覆盖它就等于改了可读性。
  2. 压缩器会改语义。 clean-css 会吞掉媒体查询，源码正确不代表产物正确，验证必须落在产物上。
  3. CDN 让”部署成功”不等于”用户看到”。 静态资源的缓存键是 URL，不是内容；不改 URL 就等于没发布。

最后一点体会：皮肤的克制程度，取决于你愿意为”以后能升级主题”付多少代价。这次所有改动都限制在一个样式表和一个脚本里，主题目录只动了两处必须动的地方——一处是移动端 SVG 的宽高比，一处是构造函数里的局部常量命名。剩下的都留在自己的文件里。下次主题升级时，冲突面就是这两个点。
