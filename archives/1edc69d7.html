【踩坑】GitHub README 里的图片为什么会永久裂开：camo 代理与缓存语义

发表于2026-11-10|更新于2026-11-10|技术笔记
|浏览量:

README 里的图片为什么会永久裂开

自己写了一个数据统计卡片服务，给 GitHub Profile README 生成动态 SVG：GitHub 贡献、LeetCode 题数、CSDN 阅读量、B 站粉丝数，拼成一张卡片，README 里放一个 <img> 指过去。

上线之后遇到过几次卡片裂开。每次的现象都一样：服务恢复了，README 还是裂的，而且要裂很久。手动刷新没用，重启服务没用，最后往往是隔天自己好了——或者干脆不好。

这篇文章是那次排查的完整结论。

第一层：为什么换图床没用

第一步自然是怀疑图床。把卡片地址从 raw.githubusercontent.com 换成 jsDelivr，再换成别的镜像——没有任何变化。

因为在 GitHub 上，README 里的外链图片根本不会直连你的源站：

flowchart LR
    A[README 里的 img 标签] --> B[GitHub 渲染时重写地址]
    B --> C[camo.githubusercontent.com]
    C --> D{缓存中是否已有结果}
    D -->|有| E[直接返回缓存内容]
    D -->|没有| F[camo 去回源取图]
    F --> G[你的图床或服务]

GitHub 会把所有外链图片重写成 camo.githubusercontent.com 的代理地址，由 camo 统一回源。也就是说：

  • 你在 README 里写的是什么域名，只影响 camo 回源的那一跳；
  • 用户看到的图片，永远来自 camo 的缓存；
  • 你换图床，改的是最后一跳，而问题出在中间那一跳。

这一步的结论是：问题的位置在 camo 的缓存策略上，不在图床上。

第二层：camo 把 5xx 当成”结果是坏的”记住了

继续往下查，看到两条关键事实。

一、camo 会缓存错误结果。 当回源拿到 5xx 时，camo 不会当作”这次失败、下次重试”，而是把”这个地址取不到内容”当成一个结论存下来。存下来之后，后续请求直接返回这个结论。所以：

服务抖动一次 → camo 记住”这里没有图” → 之后每次渲染 README 都是裂的 → 服务恢复了也没用，因为 camo 不再回源了。

二、这两类域名在同一个网段。 camo.githubusercontent.com 和 raw.githubusercontent.com 解析到同一片 185.199.x.x。所以在某些网络环境下，”camo 连不上回源”和”浏览器连不上 raw 域名”是同一个原因，换图床自然解决不了。

到这里，修法就清晰了——没有任何办法让 camo 不缓存错误。唯一能做的是让自己永远不产生错误。

三层修法

第一层：上游出问题时返回 200 加降级卡，而不是 5xx

这是最反直觉、也是最重要的一条。原来的处理是”数据源挂了就抛异常”，接口返回 500。改成：

上游情况原状态码改后状态码
数据源超时、限流、连接失败500200 + 降级卡
渲染过程抛异常500200 + 降级卡
参数不合法400400（保持）
用户不存在404404（保持）

只有”这个请求本身是错的”才返回 4xx；只要是”服务这边暂时不行”，一律返回一张能看的降级卡。降级卡上写清是哪个数据源没取到，视觉上仍然是一张正常的卡片。

async function renderCard(params) {
  try {
    const data = await Promise.allSettled(sources.map(fetchSource))
    const ok = data.filter(d => d.status === 'fulfilled')
    if (ok.length === 0) return degradedCard('数据源暂时不可用')
    return buildCard(merge(data))
  } catch (err) {
    // 关键：异常也返回 200
    return degradedCard('渲染异常', err.message)
  }
}

对应的响应状态码统一是 200。这一条把”永久裂图”变成了”短暂显示降级卡”——降级卡的缓存时间短，上游恢复后很快会被替换掉。

第二层：命中缓存时必须回放缓存头

这一层是最隐蔽的，也是排查时间最长的一层。

卡片本身在服务端做了缓存。逻辑是”命中缓存就直接返回缓存内容”。看起来没问题，实际上命中路径只回放了白名单里的几个头（content-type 之类），cache-control 被丢掉了。

后果是一条完整的链路：

flowchart TD
    A[命中缓存] --> B[只回放 content-type 等白名单头]
    B --> C[cache-control 缺失]
    C --> D[Vercel 给没有 cache-control 的响应补 max-age=0]
    D --> E[CDN 判定不可缓存]
    E --> F[每个用户请求都打到源站]
    F --> G[源站被缓存穿透打垮]
    G --> H[返回 5xx]
    H --> I[camo 永久记住裂图]

注意这条链路的终点又回到了第一层那个”永久裂图”。所以这不是性能问题，它是可用性问题：因为没回放缓存头，CDN 从没缓存过，所有流量直达源站，源站一垮 camo 就记住错误。

修法是两层都做：

// 命中缓存的路径也要带完整缓存头
function cacheHeaders(hit) {
  return {
    'content-type': 'image/svg+xml; charset=utf-8',
    'cache-control': hit
      ? 'public, max-age=300, s-maxage=3600, stale-while-revalidate=86400'
      : 'no-store',
    'x-cache-status': hit ? 'HIT' : 'MISS',
  }
}

三个指令各管一段：

  • max-age=300：浏览器缓存 5 分钟，避免用户连续刷新打源站。
  • s-maxage=3600：CDN 缓存 1 小时，这是扛住流量的那一段。
  • stale-while-revalidate=86400：CDN 里的副本过期后，先返回旧副本，同时在后台回源更新。这一条是关键——它让”源站慢”和”用户看到裂图”在时间上解耦。源站要 3 秒才响应？用户拿到的是 1 小时前的旧卡片，不是空白。

加一个能自证的响应头：x-cache-status: HIT/MISS。这是排查这类问题时唯一可靠的判据——不要靠”感觉快了”判断 CDN 有没有生效，看这个头。

第三层：进程内缓存加熔断，因为远端缓存太慢

第二层做完，CDN 开始正常缓存了。但还有一个问题：CDN 未命中的那部分请求，源站在做什么？

实测数据是扎心的：

操作实测耗时
Redis PING480ms
MongoDB Atlas 建连1–1.7s

也就是说，如果每个请求都同步去等远端缓存，光是”取缓存”这个动作就要半秒起。CDN 只要有一波抖动，源站就会因为排队而雪崩。

所以加了两层：

// 进程内 L1 缓存
const l1 = new Map() // key -> { value, expireAt }
const L1_TTL = 60_000
const L1_MAX = 500

function getL1(key) {
  const hit = l1.get(key)
  if (!hit) return null
  if (hit.expireAt < Date.now()) { l1.delete(key); return null }
  return hit.value
}

function setL1(key, value) {
  if (l1.size >= L1_MAX) l1.delete(l1.keys().next().value) // 简单淘汰
  l1.set(key, { value, expireAt: Date.now() + L1_TTL })
}
// Redis 熔断：连续失败就短路 60 秒，不等超时
let failures = 0
let openUntil = 0

async function readL2(key) {
  if (Date.now() < openUntil) return null // 短路，不发起请求
  try {
    const v = await redis.get(key)
    failures = 0
    return v
  } catch {
    if (++failures >= 3) openUntil = Date.now() + 60_000
    return null
  }
}

熔断的意义不是”少报错”，而是把 480ms 的等待变成 0ms。远端挂掉时，宁可全部走 L1 加降级卡，也不要每个请求都去等半秒然后超时。

顺带踩到的两个坑

清缓存的接口自己被缓存了

写完缓存，自然要写一个清缓存的接口。第一版：

app.delete('/api/cache/clear', (req, res) => { /* 清缓存 */ })

调用两次，第二次返回的和第一次一模一样——清缓存接口自己被缓存中间件缓存了。

修法是缓存中间件必须放行非 GET/HEAD：

function cacheMiddleware(req, res, next) {
  if (req.method !== 'GET' && req.method !== 'HEAD') return next()
  // ... 其余逻辑
}

这条规则不只适用于这个项目。任何”带副作用”的请求，只要经过缓存层，都必须显式放行，不能靠”没人会缓存 POST”这个假设。

清缓存要全量，通配符不好使

另一个坑：传 pattern=* 想把所有缓存清掉，结果什么都没清。最终改成显式的全量参数 ?all=true 才生效。

通配符匹配在这种场景下经常是”看起来支持、实际不匹配”的状态——因为 key 里含命名空间前缀或者其他分隔符，* 匹配不到。清缓存这种操作失败必须能被发现，所以返回体里要带上清了几个 key，写日志，不能只回一个 success: true。

小结

这次排查真正的收获是认识到：这四层问题其实是一条链路。

flowchart TD
    A[没回放 cache-control] --> B[CDN 不缓存]
    B --> C[流量直达源站]
    C --> D[源站等远端缓存超时]
    D --> E[排队 雪崩 返回 5xx]
    E --> F[camo 把 5xx 当结论缓存]
    F --> G[README 永久裂图]

三个结论：

  1. 对外的图片服务不能返回 5xx。 不是你这边少报错，是下游的缓存策略会把 5xx 变成永久状态。上游问题一律降级成 200 加降级卡，只有请求本身错了才用 4xx。
  2. 命中缓存的路径必须回放缓存头。 只回放 content-type 这类”内容头”、丢掉 cache-control，等价于从没缓存过。
  3. 判断缓存是否生效，看响应头，不要凭感觉。 x-cache-status 这类自证字段应该在设计缓存时一起设计进去，而不是等排查时才想起来加。

如果只记一句话：缓存的边界条件，比缓存的命中率更重要。
