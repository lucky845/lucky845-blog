【AI】多 Agent 协作编排：什么时候真的需要，怎么搭才不塌

发表于2026-11-09|更新于2026-11-09|AI
|浏览量:

1. 先说结论：多 Agent 不是银弹，九成的活儿一个 Agent 就能干

2026 年这波多 Agent 热潮里，最常见的失败模式是：把一个本来单 Agent 就能做完的任务，拆成三四个 Agent 互相传话，最后成本翻三倍、延迟翻四倍、准确率还降了。

原因很简单——Agent 之间传的是自然语言，自然语言是有损压缩。

单 Agent 内部，上下文是连续的，它记得自己刚才查到什么；一旦拆开，A Agent 的探索过程必须压成一段话讲给 B，丢掉的关键细节再也要不回来。

所以在动手编排之前，先问一个问题：这个任务真的需要多个执行者同时存在吗？

需要的情况通常只有三种：

  1. 并行：任务天然可分片，且分片之间无依赖（比如同时调研 5 个竞品）
  2. 隔离：不同子任务需要不同的上下文或不同的权限（比如一个能读代码，一个能写代码）
  3. 对抗：需要一个「蓝军」专门找另一个 Agent 的错

除此之外，用单 Agent + 更好的工具，胜率更高。

2. 三种可靠的多 Agent 形态

2.1 主管 —— 工人（Supervisor / Worker）

最常用也最稳的形态。主管只做两件事：拆任务、汇总结果。工人各自独立执行，互不通信。

      [Supervisor]
     /      |      \
Worker1  Worker2  Worker3
   |        |        |
片段A     片段B     片段C
     \      |      /
      [汇总输出]

关键点：

  • 工人之间不通信。要通信就说明任务该由主管重新拆。
  • 主管的上下文要保持轻。它不该读工人读到的一切细节，只读结构化返回（结论 + 证据摘要 + 置信度）。
  • 工人返回格式必须固定，否则主管要做模糊解析，出错率高。

2.2 流水线（Pipeline）

任务有明确阶段依赖时用：调研 → 大纲 → 写作 → 审校 → 定稿。

重点是阶段之间要有可校验的中间产物。中间产物是结构化文件（JSON / Markdown with schema），不是「一段自然语言描述」。没有中间产物，链路一断就从头再来。

2.3 辩论（Debate / Critic）

同一问题让两个 Agent 分别作答，再让第三个 Agent 判定。适合主观性强、需要多角度的任务（方案评估、代码审查）。

成本是单 Agent 的 3 倍，只在准确率收益明显时才用。

3. 上下文隔离才是多 Agent 的最大价值

很多人把多 Agent 理解成「并发」，其实它的核心价值是 上下文隔离。

一个典型例子：主 Agent 主线程负责对话，同时要读 20 个文件做代码审查。如果放在主线程，20 个文件的全文会永久占据上下文，后续对话全部被稀释。

拆出去以后：

  • 子 Agent 在自己的上下文里读那 20 个文件
  • 只把「发现了 3 个问题：文件名 行号 建议」回传主线程
  • 主线程的上下文只增加约 200 token

这叫「上下文预算的转移支付」。同一份信息，放在需要它的地方，用完就释放。

sequenceDiagram
    autonumber
    participant M as 主 Agent
    participant S as 子 Agent
    participant F as 文件系统

    M->>S: 派发审查任务
    S->>F: 逐文件读取
    F-->>S: 全文约 120k token
    Note over S: 全文只活在子上下文
    S->>S: 只留问题行
    S-->>M: 3 个问题约 200 token
    Note over M: 主上下文仅 +200 token

图里最关键的是两条虚线与那两个 Note：全文只在子 Agent 内部流转，主线程拿到的永远是压缩后的结论。上下文隔离不是「并行加速」，而是把大块信息关在该关的地方。

4. 通信协议：结构化优先，自然语言兜底

Agent 之间怎么传消息，直接决定了系统的可靠性和可观测性。

分层建议：

场景传什么
任务派发结构化：{role, objective, inputs, expected_output_schema, constraints}
中间结果结构化为主，长文本放文件，只传路径 + 摘要
失败回传结构化错误对象：{stage, error_type, retryable, partial_output}
最终汇总自然语言 + 引用来源

不要用「你去帮我查一下 xxx，然后再……」这种口语化派发。模型每次重新解析一遍意图，每次理解都可能不同。

另外，消息里一定要带约束。不写「不要修改文件」的工人，可能会顺手改代码；不写「3 分钟内返回」的工人在长任务上会卡住整个主管。

5. 失败处理：多 Agent 系统的真正难点

单 Agent 失败了，你看见的是一个错误；多 Agent 失败了，你看见的是主管卡在那里不动，不知道是谁的锅。

必须事先设计好三件事：

① 超时。每个工人有硬性超时，超时即视为失败并返回已有部分结果。不要无限等。

② 死锁检测。A 等 B 的结果，B 等 A 的结果——在有环形依赖的编排里真的会发生。给任务图做拓扑排序，有环直接拒绝启动。

③ 熔断与降级。同一个工人连续失败 3 次，主管应该降级处理（用简化版任务重试，或直接放弃该分片并在汇总里标注「缺失」），而不是重试到天荒地老。

def run_worker(worker, task, timeout=120, max_retries=2):
    for attempt in range(max_retries + 1):
        try:
            return worker.run(task, timeout=timeout)
        except WorkerTimeout:
            if attempt == max_retries:
                return PartialResult(status="timeout", data=worker.last_partial())
        except WorkerError as e:
            if not e.retryable:
                return PartialResult(status="failed", error=str(e))

注意 PartialResult 这个设计：部分成功比完全失败有价值。3 个分片里有 2 个成功，汇总时应该告诉用户「2/3 完成，第 3 部分因超时缺失」，而不是整体报错。

6. 成本与延迟：多 Agent 的真实账单

几个实测量级（仅供参考，具体取决于模型和任务）：

  • 上下文隔离型子 Agent：单次任务 token ≈ 主流程的 30%–60%，但总和因为重复读材料会超过单 Agent
  • 并行 Worker（3 个）：墙钟延迟 ≈ 最慢那个，但 token 总量 ×3
  • 辩论型：token 总量 ×3–4，延迟 ×2
  • 流水线：token 总量线性叠加，延迟也线性叠加

所以多 Agent 的正确使用姿势是：

  • 用 token 换延迟：并行分片，值得
  • 用 token 换准确率：辩论/审查，需要时值得
  • 用 token 换上下文空间：隔离子任务，几乎总是值得
  • 用 token 换「看起来更复杂」：不值得

如果一个多 Agent 方案的 token 成本是单 Agent 的 5 倍，而准确率只提升 3%，那这个方案就是负收益。

7. 编排框架：先用最小可用的

市面上的编排框架（LangGraph、AutoGen、CrewAI、各种「多 Agent 协作」库）都在解决同一件事：把「谁调用谁、传什么、失败了怎么办」写进代码。

但很多框架引入了过重的抽象，调试时你根本不知道 Agent 为什么做了那个决定。

建议的顺序：

  1. 先手写：一个 while 循环 + 工具调用 + 一个 spawn_subtask 工具，就够覆盖 80% 的多 Agent 需求
  2. 需要可视化协作图再上框架
  3. 需要持久化、断点续跑、人工介入审批时，才值得引入重型编排引擎

手写版本大致长这样：

主循环：
  1. 模型思考
  2. 若决定调用 spawn_subtask：
       - 建子任务（独立的上下文 + 受限工具集）
       - 拿到结构化结果
  3. 否则正常处理
  4. 检查预算（token / 时间 / 步数），超限则收尾

就这么点东西，90% 的场景够用了。

8. 判据：什么时候真的该多 Agent

最后给一组可操作的判断标准。满足两条以上，才考虑多 Agent：

  • 任务可以切分成无依赖的分片
  • 单个子任务需要的上下文超过主流程能承受的预算
  • 需要权限隔离（有的能写，有的只能读）
  • 需要主动对抗（审查、红蓝对抗）
  • 子任务的失败不影响主流程最终可用
  • 已经实测单 Agent 版本确实跑不动，而不是「感觉会慢」

最后一条最容易被跳过。先写单 Agent 版本，跑到瓶颈，再拆——而不是一开始就画一张漂亮的架构图，然后在里面迷路。

多 Agent 系统的复杂度不是线性的，是乘法的。每多一个 Agent，就多一组可能的失败组合、多一条要维护的消息协议、多一份要观测的日志。这笔账，得算清楚再花。
