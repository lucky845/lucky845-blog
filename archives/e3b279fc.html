【AI】Agent 成本控制：把每月账单砍掉 70% 的六个手段

发表于2026-11-09|更新于2026-11-09|AI
|浏览量:

1. 一个真实的账单

先说个具体数字。一个日均 5 万次调用的客服 Agent，改动前每月 token 成本 4.2 万元。做了三件事之后降到 1.1 万，准确率没有下降：

  1. 把系统提示词从 3200 token 压到 900 token
  2. 工具返回值从「全量 JSON」改成「摘要 + 分页」
  3. 给不同环节配置了不同档位的模型

这三件事没有一件需要模型变强，全是工程问题。

Agent 的成本控制和传统后端调优很像：先找最大那一块，别在小地方抠。

2. 先算清楚钱花在哪

一次 Agent 请求的成本由三部分构成，量级差异极大：

构成典型占比特点
输入 token（系统提示 + 历史 + 工具结果）70%–90%每轮都要重传，是复利
输出 token5%–20%单价高但量小
工具调用本身（外部 API、数据库）视情况与模型无关，但常被忽略

最容易失控的是第一项。因为多轮对话中，历史是累加的：第 10 轮的请求里包含了前 9 轮的全部内容。

如果你有一轮工具返回了 8000 token，那么从这一轮往后，每一次请求都要多付 8000 token。一个 15 轮的会话，这次工具调用的真实成本是 8000 × 剩余轮数。

这就是为什么「工具返回值要小而准」不是洁癖，是省钱。

这张图的含义很直白：成本不是随轮次线性增长，而是历史全量重传的累加。青色是月账单还能看的时候，琥珀色是账单失控的时候——中间没有缓冲带。

所以先做一件事：把每次请求的 input_token 打出来，按轮次画成曲线。你会看到很多该断裂的地方——那些断点就是优化的第一个抓手。

3. 提示词缓存（Prompt Caching）：最省事的一招

主流厂商都支持前缀缓存：请求开头如果有一段完全相同的文本前缀，这部分 token 按原价的 10%–25% 计费。

关键在于「完全相同的前缀」——缓存是从头开始匹配的，中间改一个字，后面全部失效。

所以提示词的组织顺序很重要：

[固定的系统提示]        ← 放最前面，内容永不变
[工具定义]              ← 次稳定，版本升级才变
[少量静态知识/示例]      ← 相对稳定
--- 以上可缓存 ---
[用户输入 + 对话历史]    ← 每次都变
[工具返回结果]          ← 每次都变

常见错误是把日期、用户 ID、随机 session 号写在系统提示的最开头，导致缓存永远不命中。

❌ 今天日期：2026-11-09，用户：张三，开始吧...
✅ 你是客服助手...（固定内容）
   ## 当前上下文：日期 2026-11-09，用户 张三（可变内容放末尾）

另外要注意缓存的有效期（通常 5 分钟到 1 小时不等）和最小长度门槛（有的模型要求前缀至少 1024 token 才触发）。高频场景下，缓存命中率做到 70%+ 是常见水平。

4. 上下文压缩：别把整本历史都拖着走

会话超过一定轮次后，历史必须裁剪。几种策略：

① 滑动窗口：只保留最近 N 轮。最简单，但会丢掉早期关键信息。

② 摘要压缩：把早期轮次交给一次便宜的模型调用，压成一段摘要。

def maybe_compress(messages, threshold=8000):
    if token_count(messages) < threshold:
        return messages
    old, recent = messages[:-6], messages[-6:]
    summary = cheap_model.summarize(old)   # 用便宜模型
    return [{"role": "system", "content": f"以下是更早对话的摘要：{summary}"}] + recent

③ 结构化记忆：不是压缩自然语言，而是把关键事实抽成键值对。

{
  "user_intent": "退换货",
  "order_id": "A20261109001",
  "resolved": false,
  "constraints": ["要求 7 天内寄回", "运费商家承担"]
}

结构化记忆比摘要更省，也更不容易丢关键信息——因为摘要依赖模型判断「什么重要」，而结构化记忆是设计时就定好的。

实践中最有效的组合：近期完整 + 早期结构化 + 摘要有损兜底。

5. 模型分级：不是所有环节都配得上旗舰模型

一个 Agent 流程里，真正需要「聪明」的环节往往只占少数：

环节建议档位理由
意图识别、分类小模型任务简单，量大
工具参数抽取中等模型需要一定理解力
复杂推理、规划旗舰模型决定成败
结果总结、格式化小模型纯转写
安全审核小模型 + 规则规则优先

分级之后的坑：切换模型时格式可能不兼容。小模型对 JSON 的遵循度通常更差，需要更严格的约束和重试。

6. 结构化输出：省的不只是解析成本

让模型「自由发挥」再在服务端解析，代价比想象中大：

  • 为了解析可靠性，你得写大量容错代码
  • 失败要重试，重试又要完整再跑一遍 prompt
  • 自由文本输出通常比结构化输出长 2–3 倍

用 JSON Schema / Function Calling 强制结构化输出，能同时降成本、降错误率。代价是少量格式描述 token，这笔投资几乎总是划算的。

一个小技巧：输出字段按重要性排序。如果模型在长输出中途被截断，前面的关键字段已经写完了，可以抢救。

7. 预算控制：硬性闸门比事后统计有用

不要指望「观察后再优化」，要在运行时设闸门：

budget = Budget(max_tokens=200_000, max_steps=20, max_seconds=120)

def step():
    budget.consume_tokens(resp.usage.total_tokens)
    if budget.exhausted():
        raise BudgetExceeded(budget.report())

超预算时该做什么，比阈值本身更重要：

  • 优雅收尾：用剩余预算让模型输出「目前已完成 X，剩余 Y 尚未完成」
  • 降级重试：换用小模型 + 更短的上下文再试一次
  • 明确失败：返回结构化错误，附上已消耗的资源和进度

最不该出现的是一声不响地跑满额度然后返回一个半成品。

8. 一张成本优化优先级表

按投入产出比排序，从高到低：

优先级措施典型降幅工作量
1修提示词缓存命中（固定内容前置）30%–60%半天
2工具返回值瘦身 + 分页20%–40%1–2 天
3模型分级20%–50%2–3 天
4上下文压缩策略15%–35%1 周
5结构化输出替代自由文本10%–25%1 周
6减少不必要的工具调用轮次10%–30%视架构

前两项几乎总是收益最大、最容易被忽略的，因为它们不在「模型能力」这个显眼维度上。

9. 闭环：把成本当作一等指标

降本做完不是结束，要把它变成持续可观测的指标：

  • 每次请求记录：input_tokens / output_tokens / cached_tokens / steps / latency
  • 按场景（意图分类）拆开看，找到单位成本最高的那几类
  • 设置告警：单次会话成本超 P99 的 3 倍时通知
  • 版本对比：每次提示词改动后对比成本与准确率

成本控制和效果优化是一对张力，任何一边单独极端化都会翻车——只省钱会砍掉必要的上下文导致准确率崩，只看效果会把账单跑穿。真正要做的是把这两条曲线画在同一张图上，找到拐点。

大多数团队的问题是压根没画这张图。
